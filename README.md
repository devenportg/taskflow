# Практическое задание: TaskFlow API

## Цель

Разработать REST API для управления задачами команды. Данные должны храниться в PostgreSQL, структура базы — создаваться миграциями Alembic, а приложение и база данных — запускаться в Docker Compose.

## Технологии

- Python 3.12;
- FastAPI;
- PostgreSQL 16;
- SQLAlchemy 2;
- Alembic;
- Docker и Docker Compose.

## Модель данных

Создайте ровно пять таблиц.

### `users`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | integer | первичный ключ |
| `email` | varchar(255) | обязательное, уникальное |
| `display_name` | varchar(255) | обязательное |
| `role` | varchar(32) | обязательное, по умолчанию `operator` |
| `created_at` | timestamptz | обязательное, заполняется БД |

Допустимые роли: `operator`, `admin`.

### `projects`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | integer | первичный ключ |
| `name` | varchar(200) | обязательное |
| `description` | text | может быть пустым |
| `created_at` | timestamptz | обязательное, заполняется БД |

### `labels`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | integer | первичный ключ |
| `name` | varchar(64) | обязательное, уникальное |
| `color` | varchar(7) | обязательное, по умолчанию `#6b7280` |

Цвет хранится в формате `#RRGGBB`.

### `tasks`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | integer | первичный ключ |
| `project_id` | integer | обязательный внешний ключ на `projects.id` |
| `assignee_id` | integer | внешний ключ на `users.id`, может быть пустым |
| `label_id` | integer | внешний ключ на `labels.id`, может быть пустым |
| `title` | varchar(200) | обязательное |
| `description` | text | может быть пустым |
| `status` | varchar(32) | обязательное, по умолчанию `open` |
| `priority` | varchar(16) | обязательное, по умолчанию `medium` |
| `created_at` | timestamptz | обязательное, заполняется БД |
| `updated_at` | timestamptz | обязательное, заполняется БД |

Допустимые статусы: `open`, `in_progress`, `done`. Допустимые приоритеты: `low`, `medium`, `high`.

При удалении проекта его задачи должны удаляться. При удалении исполнителя или метки соответствующее поле задачи должно становиться `NULL`.

### `comments`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | integer | первичный ключ |
| `task_id` | integer | обязательный внешний ключ на `tasks.id` |
| `author_id` | integer | обязательный внешний ключ на `users.id` |
| `body` | text | обязательное, непустое |
| `created_at` | timestamptz | обязательное, заполняется БД |

При удалении задачи её комментарии должны удаляться. Пользователя с существующими комментариями удалять нельзя.

## Требования к API

Для каждого ресурса реализуйте пять операций:

| Метод | URL | Результат |
|---|---|---|
| `GET` | `/v1/{resource}` | список записей |
| `GET` | `/v1/{resource}/{id}` | одна запись |
| `POST` | `/v1/{resource}` | создание записи |
| `PATCH` | `/v1/{resource}/{id}` | частичное обновление |
| `DELETE` | `/v1/{resource}/{id}` | удаление записи |

Значение `{resource}`: `users`, `projects`, `labels`, `tasks` или `comments`.

Дополнительно реализуйте:

- `GET /health` — проверяет соединение с БД и возвращает `200`;
- фильтр `GET /v1/tasks?project_id=1&status=open`;
- фильтр `GET /v1/comments?task_id=1`;
- интерактивную документацию по адресу `/docs`.

### Поведение API

- `POST` возвращает `201` и созданную запись;
- успешные `GET` и `PATCH` возвращают `200`;
- успешный `DELETE` возвращает `204` без тела;
- запрос несуществующей записи возвращает `404`;
- ошибка входных данных возвращает `422`;
- дубликат уникального значения или нарушение внешнего ключа не приводит к `500`, а возвращает понятную ошибку `409`;
- запросы и ответы описаны Pydantic-моделями; служебные поля клиента не принимаются;
- SQL-запросы выполняются через SQLAlchemy, а не строками в роутерах.

## Миграции

1. Настройте Alembic на подключение к PostgreSQL через переменную окружения `DATABASE_URL`.
2. Создайте начальную миграцию со всеми пятью таблицами, внешними ключами и ограничениями.
3. Реализуйте как `upgrade()`, так и `downgrade()`.
4. Приложение не должно создавать таблицы через `Base.metadata.create_all()` — схема изменяется только миграциями.

Проверка миграций:

```bash
alembic upgrade head
alembic downgrade base
alembic upgrade head
```

## Docker

Добавьте:

- `Dockerfile` для API;
- `.dockerignore`, исключающий как минимум `.git`, `.venv`, `__pycache__` и `.env`;
- `docker-compose.yml` с сервисами `api` и `db`;
- именованный volume для данных PostgreSQL;
- `.env.example` без реальных секретов.

Требования к запуску:

- API внутри контейнера слушает `0.0.0.0:8000`;
- API подключается к БД по имени сервиса `db`, а не через `localhost`;
- миграции автоматически применяются при старте API;
- после `docker compose up --build` API доступен на `http://localhost:8000`;
- данные PostgreSQL сохраняются после перезапуска контейнеров.

## Как проверить работу

```bash
docker compose up --build
curl http://localhost:8000/health
```

Затем через `/docs`:

1. Создайте пользователя, проект и метку.
2. Создайте задачу со ссылками на них.
3. Добавьте к задаче комментарий.
4. Получите задачу и списки с фильтрами.
5. Измените статус задачи на `done`.
6. Удалите проект и убедитесь, что связанные задачи и комментарии удалены.
7. Перезапустите Compose и убедитесь, что остальные данные сохранились.
